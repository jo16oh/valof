# 14.29 Rule: `readonly` in a payload, 2026-11-18

**Adopted.** `no-readonly-payload` reports a `readonly` written in a payload: `readonly T[]`,
`readonly [A, B]`, a `readonly` property modifier, `Readonly<…>` and `ReadonlyArray<…>`.

```ts
type Post = Val<"Post", { tags: readonly string[] }>;
//                              ^ a Val's payload is already readonly; drop `readonly`, since
//                                `Val.unwrap` returns the payload as written
```

§3 says not to write it. `Val` makes the payload deep-readonly anyway, and `Val.unwrap` returns the
payload as written, so the copy it returns stays readonly. Nothing enforced the guidance. `Project`
and `Patterns` in valof-lint carried `readonly string[]` until a review found them.

## What it reads

- A top-level `type X = Val<…>`: the second type argument. For `Val.Record<…>`, the value type, its
  third.
- A top-level `type X = Enum<…>`: each variant's payload in the variant record, and the third type
  argument. The shared fields arrive there intersected with the tag and the traits.

Inside a payload, the walk follows object types, arrays, tuples, unions, intersections, and the type
arguments of `Readonly<…>` and `ReadonlyArray<…>`. Every other type reference ends the walk. A Val
declared inside a function or a test is not read, the same as for every rule about aliases.

## It warns

The code works, and the payload is readonly either way. The `readonly` affects only the type of the
copy `Val.unwrap` returns. The plugin's `recommended` sets it to `warn`, as it does every rule whose
finding leaves the code around it working.

## Each spelling gets its own message

The message names what to write: drop `readonly`, write the type `Readonly<…>` wraps, or write `T[]`
for `ReadonlyArray<T>`.

## Rejected: following an alias the payload references, 2026-11-18

`{ tags: Tags }` with `type Tags = readonly string[]` goes unreported. Following `Tags` needs the
file's aliases and its imports. It would also report an alias that other code uses outside any
payload, where the `readonly` is right. A missed finding costs the user a readonly copy, and a false
one asks them to change a type that is correct. Like the other rules, this one reports nothing where the syntax alone does not show the type.

The names `Readonly` and `ReadonlyArray` are matched by name. A local type that shadows either is
reported as if it were the global one.

## The payloads it changed

- `readonly` was dropped from four payloads in `src/lib/enum.test.ts` and `src/lib/val.test.ts`. The test "a
  readonly array in the declaration stays readonly" keeps it, since that is its subject. The rule
  does not see any of them, because they are declared inside a test.
- `readonly` was dropped from `scripts/check-dist/check/types/fixtures/core.ts` and `enum.ts` too. No
  comment or commit tied it to the measurement. Without it, core measured 12,977 → 12,984
  instantiations and enum 56,993 → 56,999, both within budget. The self test does not lint
  fixtures, so the rule did not require this change.
