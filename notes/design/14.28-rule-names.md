# 14.28 Rule names follow ESLint's `no-*`, 2026-11-14

**Adopted.** Every rule name starts with `no-`, followed by the old name. Only `incomplete-disable`
changed beyond the prefix, to `no-vague-disable`. A disable comment or a config that names a rule
needs the new name.

```
unused-member        → no-unused-member
duplicate-brand      → no-duplicate-brand
brand-mismatch       → no-brand-mismatch
bypassed-companion   → no-bypassed-companion
incomplete-disable   → no-vague-disable
…
```

A user writes the names in an ESLint or Oxlint config next to rules from other plugins, as
`valof/no-unused-member`. The old names stated only the defect, without ESLint's `no-`, so they
read differently from every rule beside them.

The old name stays after the prefix. Each one was chosen against rejected alternatives (§14.18,
§14.24), and a user migrating adds three characters rather than learning a new name. A rule added
later takes the same shape: `no-` and the defect.

The source files and the fixture directories take the new names too, so they still match the kinds
character for character (§14.11).

## The command takes `--skip` and `--enable`

`--no-<kind>` left a rule out of the run, so `no-unused-member` would be skipped with
`--no-no-unused-member`. `--<kind>` turned an opt-in rule on, so `--no-data-type-outside-valof`
would turn a rule on with a flag that reads as turning it off.

Both became flags that take a rule, after a space or an equals sign:

```
valof-lint --skip no-unused-member --skip=no-duplicate-brand
valof-lint --enable no-data-type-outside-valof=classes,constraints
```

`--enable` with a rule on by default is refused, with the same message as a typo. It lists the rules
off by default. `--project` with no value now fails with `MissingValueError`, as `--skip` and
`--enable` do.

## Rejected: `prefer-*`

`prefer-companion` for `bypassed-companion` and `prefer-valof-data-type` for
`data-type-outside-valof`. "Prefer" reads as a suggestion. Both rules report a defect the user is
expected to fix, so `no-` fits them as it fits the rest.

## Rejected: names that drop the old one

`require-val-of-type` for `inferred-val-of`, `brand-name-matching` for `brand-mismatch` (after
ESLint's `func-name-matching`), and `no-state-in-impl` for `hidden-shared-state-in-impl`. Each reads
well on its own, but the set no longer follows one naming pattern, and a user can no longer derive
the new name from the old one.

## `incomplete-disable` → `no-vague-disable`

The rule reports a directive that names no rule, and one that names no scope. `vague` covers both.
The directive does not say what it silences, or where.

- **Rejected: `no-unlimited-disable`.** It is the name eslint-comments uses, but "unlimited" fits
  only the directive that names no rule. A directive with no scope silences nothing, so it is not
  unlimited.
- **Rejected: `no-blanket-disable`.** Ruff's `blanket-noqa` reports the same directives, and has the
  same mismatch.
- **Rejected: `no-bare-disable`.** The name before §14.18, which covered only the directive that
  names no rule.
- **Rejected: `no-unscoped-disable`.** Here a scope means a line or a file, so the name leaves out
  the directive that names no rule.
- **Rejected: split it into two rules,** one per missing part, matching eslint-comments'
  `no-unlimited-disable` and `disable-enable-pair`. The fix for both is the same, to write what is
  missing.

No other linter reports a directive with no scope. In ESLint, `/* eslint-disable */` has a scope,
until `eslint-enable` or the end of the file. A bare `valof-lint-disable` silences nothing, and
making it silence the whole file was rejected in §14.16.
