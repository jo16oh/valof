# 14.30 Rule: an import from `valof/internal/*`, 2026-11-18

**Adopted** (user). `no-internal-import` reports an import or a re-export whose module is under
`valof/internal/`.

```ts
import type { Nocopy } from "valof/internal/val";
//                          ^ `valof/internal/*` is exported for declaration output, and can change
//                            in any release; import from `valof`
```

`package.json` exports `./internal/*` so a user's emitted declarations can name the types the entry
leaves out (§18.4, §18.7). An editor offers that path when it completes an import, so a user can
reach an internal type without meaning to. A user imports from `valof`. The internal paths can change
in any release.

## What it reads

An `import`, an `export { … } from` and an `export * from` whose module is a path under
`valof/internal/`. It reports the module name. The parser's tree does not mark a type-only import,
so the rule reads every import alike. `valof/internal` with nothing after it is not read, since
`exports` resolves only a path under it.

Not read: an `import("…")`, as a type or as a dynamic import. The parser's tree gives neither a
node of its own. Declaration output writes the type form, and a user does not.

## It warns

The import works until the internal module changes. The plugin's `recommended` sets it to `warn`, as
it does every rule whose finding leaves the code working (§14.29).

## Rejected: `@deprecated` on the exported internal types

Every type the internal modules export would carry it, so valof's own source would show the
strikethrough at each use. An editor reports a deprecation only where the source names the type, and
a user sees these types in a hover or in declaration output, where nothing is reported. The types
also stay, because declaration output needs them.
